## Behavior and files

- `frontend/src/app/(protected)/orders/page.js`: shows the whole-order percentage, maximum KES and remaining allowance beside discounts and in the review/phone submit area. An excessive discount is marked immediately. Submit errors identify a control or clothing section, show an inline explanation, and scroll/focus it. The review and phone action area repeat the error with Go to field. Customer, service, quantity, date, clothing, discount reason, promised time and payment checks retain their business rules.
- Policy retrieval runs on initial entry, return to a visible/focused tab, and Start next order. Focus/visibility reads share one in-flight request. An unavailable policy permits no new employee discount; setup can still load customers/services. Failed authentication pauses setup until password reentry finishes. There is no polling and no live push; FastAPI remains authoritative at save time.
- `frontend/src/context/auth-context.js`, `frontend/src/lib/request-feedback.js`, `frontend/src/components/layout/request-status.js`, `frontend/src/app/layout.js`: track concurrent requests through the shared API/auth boundary. A save has display priority over reads. A small reduced-motion-aware spinner labels the actual operation; after eight seconds it gives a waiting instruction. It does not claim success, percentage completion, automatic save retry or a diagnosed transient error. Routine background token renewal remains quiet. Labels contain no record IDs, request bodies, credentials or URLs.
- `frontend/src/components/orders/pending-save-notice.js`: a normal in-flight save uses progress feedback; an uncertain outcome still reveals and focuses Retry previous save. The stored body/key are unchanged. Recovery and order-error scrolling respect reduced-motion preferences.
- `frontend/src/app/globals.css`: rejected controls/sections have a red boundary and scroll margin. Labels, inline explanations, aria-invalid/aria-describedby and polite status announcements support keyboard and assistive-technology use.
- `frontend/src/lib/api.js`: only GET/HEAD reads outside auth may retry network TypeError or HTTP 502/503/504, up to two retries, with 500/1,000 ms base delays plus up to 250 ms jitter. A readable Retry-After is a minimum; HTTP 429 without a usable header is not retried. Fetch, waits and body parsing share the existing 30-second deadline. Cancellation stops new attempts. Login, writes, permanent/validation failures and malformed successful replies are never automatically repeated.
- `frontend/tests/read-retry.test.mjs`: capped delays/recovery, Retry-After seconds/date, over-budget waits, shared timeout, cancellation, no write/login/permanent-error repeats and safe concurrent feedback priority.

The current cross-origin backend does not expose Retry-After through CORS. Browser-hidden headers are treated as absent; 429 therefore stays an explicit wait instruction. This increment does not change backend permissions, discount calculations, migrations, database access or dependencies.
